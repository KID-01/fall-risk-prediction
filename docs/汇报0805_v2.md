> 汇报日期：2026-08-05

> 说明：本文只把代码中已经存在或可以由仓库直接验证的内容写成“已完成”；文档规划、预期输出和代码框架不等同于真实运行结果。

## 一、项目简介

项目面向居家和社区养老场景，目标是通过视频中的人体姿态和步态变化，提前发现老人跌倒风险。

系统当前采用两条技术路径：

- **规则引擎路径：当前主要可演示路径。** 通过关键点、四项步态特征、个体化基线、偏离检测和四级预警完成风险判断。
- **深度模型路径：模型结构和训练代码已建立，训练数据与权重正在迭代中，尚未实装到当前推理链路。**

## 三、已经完成的工作

### 1. 视频和姿态处理代码已打通

`src/data/` 已形成从视频到关键点的处理模块：

```text
VideoCapture → HumanDetector → 姿态提取 → 帧质量过滤 → KeypointFrame
```

目前有两个姿态后端：

- `MediaPipe PoseLandmarker`：输出 33 个关键点；
- `YOLOv8n-Pose`：输出 COCO 关键点，再映射为统一的 33 点格式。

`configs/base.yaml` 当前配置为 `yolo_pose`，模型缺失时会尝试自动下载 `yolov8n-pose.pt`。这说明代码路径已实现，但当前仓库尚未接入训练中的项目权重和完整运行环境，本次不能把真实视频推理写成“已验证”。

### 2. 四项步态特征已经实现

`src/inference/features.py` 包含四个计算器：

| 特征 | 代码中的计算含义 |
|---|---|
| 行走节拍 | 髋部坐标时序的 FFT 主频 |
| 步幅幅度 | 踝部摆动幅度，并按躯干高度归一化 |
| 躯干稳定 | 肩髋几何关系的角度变化 |
| 活动密度 | 时间窗口内的活动比例 |

这些计算器被 `FeatureCalculator` 统一调用，输出四维 `FeatureVector`。

### 3. 个体化基线和双层偏离检测已经实现

`src/inference/baseline.py` 和 `src/inference/deviation.py` 已有对应实现：

- 基线管理：按人员保存特征样本，计算均值、标准差和协方差逆矩阵；
- 短期检测：5 分钟窗口、马氏距离、连续超阈值窗口判断；
- 长期检测：最多保留 14 天日均特征，用线性回归计算趋势斜率。

当前配置中的关键参数是：基线至少 100 个样本，短期马氏距离阈值 3.0，连续 3 个窗口触发，长期趋势阈值为 -0.05。

### 4. 监控主链路和分级预警已经实现

`src/inference/monitor.py` 的 `FallRiskMonitor` 已整合：

```text
视频帧 → 人体检测 → 姿态提取 → 帧过滤 → 特征计算
→ 基线采集/对比 → 偏离检测 → AlertEngine → 数据库记录
```

`src/alerts/engine.py` 实现四级风险状态：低风险、关注级、预警级、高危级。高危判断包括长时间无活动，以及短期和长期偏离同时出现等情况。

需要注意：当前代码有短期偏离计数和事件日志，但没有看到独立的告警冷却/去重状态机，因此“告警去重”仍应列为后续工作。

### 5. 后端 API、WebSocket 和数据库已经具备

`src/api/` 已提供：

- `POST /api/v1/stream/start`、`POST /api/v1/stream/stop`：启动和停止监控；
- `GET /api/v1/risk/current`、`GET /api/v1/risk/history`：当前和历史风险；
- `POST /api/v1/baseline/reset`：重置基线；
- `GET /api/v1/alerts`、`POST /api/v1/alerts/{id}/acknowledge`：查询和确认告警；
- `GET /api/v1/stats`：统计数据；
- `WS /ws/alerts`：实时消息通道。

数据库模块已实现风险记录和告警事件的 SQLite 持久化。集成测试也覆盖了风险记录和告警事件写入逻辑，但使用的是合成数据和 Mock 视频源。

### 6. 前端看板源码已经完成

`frontend/src/App.jsx` 和 `frontend/src/index.css` 已实现家属端看板，包含风险等级卡片、风险评分仪表盘、趋势图、告警列表、监控控制按钮、WebSocket 连接和明暗主题切换。

当前仓库只有前端源码和依赖清单，没有发现已构建的 `frontend/dist/`；因此前端需要先安装依赖并运行 Vite，不能直接把生产构建写成已验证。

### 7. 数据工具和模型代码框架已经建立

已经存在以下工具或模块：

- 视频采集、预处理、关键点提取和 `.npy` 关键点存储；
- PyTorch `FallRiskDataset`，含固定长度时序采样和数据增强；
- LabelStudio 导入、导出和标注一致性计算脚本；
- DVC 配置和数据版本管理文件；
- `FallRiskPredictor`：Transformer 时序编码器、多模态融合和风险预测头；
- `scripts/train.py`：训练、验证、早停和 `best.pt` 保存逻辑；
- `src/ezviz/client.py`：Token、设备列表、直播地址和云台控制接口。

## 五、当前主要阻塞点

### 1. 深度模型正在训练，尚未实装到推理链路

`FallRiskPredictor` 的网络结构和损失函数已写好，但：

- 训练数据和标签正在整理、训练和迭代中，尚未以可复现数据包接入当前仓库；
- 当前仓库的 `scripts/train.py` 仍调用 `create_dataloaders(..., labels=None)`，训练标签接入入口仍是 TODO；
- 如果直接按当前脚本入口运行且未传入标签，`FallRiskDataset` 会使用默认 `risk_score=0.0`、`risk_level=0`；
- 训练中的权重尚未实装到当前仓库的 `checkpoints/`，因此暂时没有可复现的模型评估结果。

因此，深度模型目前应表述为“结构和训练流程已完成，训练正在进行，权重和评估结果尚未实装到当前推理链路”，不能把训练中的阶段性结果表述为已上线模型指标。

### 2. 多模态环境输入尚未形成完整模块

模型接口预留了 5 维 `env_feat`，训练代码在缺少环境特征时用零向量补齐；但 `src/edge/` 目前只有初始化文件，没有完整的环境风险感知和边缘处理实现。

### 3. 真实设备和真实视频链路尚未完成验证

萤石 SDK 客户端代码已经存在，但当前仓库没有真实设备配置文件，也没有随仓库提交设备视频数据。训练中的模型和真实 RTSP 拉流、持续推理、断流重连及家属端完整闭环仍需现场验证。

### 4. 性能和部署还没有实测证据

Docker 配置文件已经存在，但当前没有运行结果；真实视频端到端延迟、CPU/GPU 占用、误报率、漏报率和预警提前量也尚未形成报告。

### 4. 总体结论

当前项目可以准确表述为：
