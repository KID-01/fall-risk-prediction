# 跌倒风险预测系统后续方案

> 版本：V1.0  
> 编写日期：2026-08-05  
> 基础：当前仓库代码状态与新增设计要求

## 一、当前基线

目前已经具备：

- 视频采集、人体检测、MediaPipe/YOLO-Pose 姿态提取；
- 四项步态特征、个体化基线、短期/长期偏离检测；
- 四级规则预警、FastAPI、WebSocket、SQLite 和 React 看板；
- `FallRiskPredictor` 模型结构和训练脚本；
- 138 个测试函数，含核心逻辑、标注工具、姿态映射和合成数据集成测试。

当前缺口：

- 训练数据、标签和模型权重正在迭代中，但尚未形成可复现版本并实装到当前推理链路；
- 当前模型是 Transformer，不是 ST-CNN；
- 没有跌倒/蹲下/躺卧动作分类器；
- 没有多人跟踪、15 米标定和真实视频性能数据；
- 没有声光报警、移动 APP、急救平台和位置联动；
- `src/edge/` 尚未形成边缘处理器；
- 没有人脸模糊、完整关键点脱敏和 HIPAA 合规实现。

## 二、总体实施路线

```text
真实数据采集与标注 → 动作识别模型 + 姿态角/加速度特征
→ 多人跟踪与风险融合 → 边缘端推理与隐私处理
→ 500ms 多通道告警链路 → 真实场景测试、指标验收和部署
```

## 三、阶段一：数据和标签先行

### 目标

将正在训练使用的数据和标签整理为可复现版本，支持动作分类和误报率评估，避免当前代码入口继续依赖默认标签或合成特征。

### 工作内容

1. 采集正常行走、站立、坐下、蹲下、躺卧、起身、跌倒等动作。
2. 覆盖单人、多人遮挡、不同光照、不同视角和不同距离。
3. 使用 LabelStudio 标注动作类别、关键点和时间区间。
4. 按人员划分训练集、验证集和测试集，避免同一人的相邻帧泄漏到不同集合。
5. 为每段样本记录摄像头距离、分辨率、帧率和场景条件。

### 交付物

- `data/keypoints/` 关键点序列；
- 动作标签文件：`fall / squat / lying / walking / sitting / standing`；
- 按人员隔离的 train/val/test 划分文件；
- 数据集统计报告和标注一致性报告。

## 四、阶段二：精准判定模型

### 目标

实现连续动作轨迹分类，并将跌倒与蹲下、躺卧等相似行为区分开。

### 推荐实现

1. 新增 `src/models/st_cnn.py`，输入连续关键点序列 `(T, K, C)`。
2. 时间维使用 1D/3D 卷积，关键点维建模关节之间的空间关系。
3. 在模型输入中加入躯干倾角、角速度、髋膝踝高度变化、关键点速度和加速度、可见性和帧质量。
4. 输出动作类别和跌倒置信度，再与当前规则引擎融合。
5. 保留规则引擎作为可解释的兜底判断，模型与规则冲突时记录原因。

### 验收指标

- 跌倒召回率、精确率、F1；
- 误报率 < 5%；
- 跌倒与蹲下、躺卧的混淆矩阵；
- 不同人员、不同距离和不同光照下分别统计结果。

## 五、阶段三：多人和距离能力

### 工作内容

1. 从“选择最高置信度人体”改为返回全部人体检测框和关键点。
2. 增加 ByteTrack、SORT 或等效跟踪器，为每个人生成稳定 ID。
3. 为每个 ID 分别维护关键点缓存、基线、风险状态和告警状态。
4. 设计遮挡、人员进出画面和 ID 切换处理。
5. 使用实际摄像头完成 3m、5m、10m、15m 测试，记录检测率和关键点有效率。

### 验收指标

- 单人和多人场景均能独立输出风险；
- 人员 ID 在短时遮挡后能够恢复；
- 15 米处仍能达到约定的人体检测和关键点有效率；
- 形成相机型号、镜头、分辨率和安装高度说明。

## 六、阶段四：500ms 多通道告警

### 工作内容

1. 在采集、推理、决策、发送、设备响应各环节加入高精度时间戳。
2. 新增本地声光报警适配器，明确 USB、GPIO 或网络继电器接口。
3. 新增移动 APP 推送适配器，先支持一种稳定推送通道。
4. 设计急救平台适配层，包含位置、设备 ID、告警时间、重试和失败补偿。
5. 将 `acknowledge` 扩展为“误报取消”状态机：触发、通知、确认、取消、关闭。
6. 增加告警冷却和去重，避免同一事件重复通知。

### 验收指标

- 从有效帧到本地报警触发的 P95 延迟 < 500ms；
- APP 推送成功率和平均延迟有统计；
- 急救平台失败时有重试和本地记录；
- 用户取消误报后，相关报警通道全部停止并保留审计记录。

## 七、阶段五：边缘隐私和合规

### 工作内容

1. 新增 `src/edge/processor.py`，在摄像头侧完成姿态推理和关键点提取。
2. 原始视频只存在内存，不落盘、不进入日志、不上传云端。
3. 增加人脸检测和模糊处理作为可选保护层。
4. 上传内容只保留关键点、特征和风险事件，并采用 TLS 和设备认证。
5. 对关键点数据做设备 ID 脱敏、访问控制、加密存储和定期删除。
6. 明确适用法规：国内部署以个人信息保护法规为主；如声称 HIPAA，需要补充 HIPAA Security Rule、Privacy Rule、审计和供应商协议等材料。

### 验收证据

- 网络抓包证明没有原始视频上传；
- 磁盘检查证明没有持续保存原始帧；
- 人脸模糊效果样例；
- 访问日志、密钥管理、删除策略和合规矩阵。

### 1. 硬件和平台原则

会议已经明确：项目必须围绕萤石平台和萤石硬件完成，不能用小米手环等第三方设备替代最终方案，也不能用公开数据流替代真实硬件采集作为最终成果。

对当前仓库的直接影响是：

- `src/ezviz/client.py` 已有萤石 Token、设备列表、直播地址和云台控制代码，应优先完成真实设备联调；
- 当前仓库没有 `configs/ezviz.yaml`，需要通过安全配置注入 `appKey`、`appSecret` 和设备信息；
- 摄像头之外至少落地一种萤石平台可对接的生理数据设备，例如血压或血糖设备；
- 生理设备必须能够完成“采集 → 传回 → 存储 → 展示”，只买设备但没有数据回传不能算完成；
- 在设备正式到位前，公开数据或模拟数据只能用于接口开发和单元测试，不能用于最终指标和最终演示结论。

### 2. 模型任务调整

会议确定的模型主线应拆为三层：

```text
YOLO：人体/物体检测 + 姿态关键点
    ↓
姿态角、速度、加速度等基础特征
    ↓
LSTM：连续行为分类与跌倒判定
    ↓
紧急告警 / 非紧急行为趋势记录
```

与当前代码的对应关系：

| 会议要求 | 当前代码 | 后续动作 |
|---|---|---|
| YOLO 人体检测 | `src/data/human_detector.py` | 接入真实萤石视频并验证检测效果 |
| YOLO 姿态识别 | `src/data/yolo_pose_extractor.py` | 保留关键点输出，补充姿态角、速度和加速度特征 |
| LSTM 行为分类 | 当前仓库没有 LSTM 模块 | 新增 `src/models/behavior_lstm.py` 和训练/评估脚本 |
| 非紧急行为记录 | 当前有风险/告警记录 | 扩展行为事件表，记录发呆、静止、停留、起床和活动时段 |
| 多模态融合 | `FallRiskPredictor` 预留 `gait_feat/env_feat` | 接入生理设备特征，明确模型输入版本和缺失值策略 |

### 3. 建议的新增模块边界

为降低跨组沟通成本，建议保持模块独立，最后通过统一接口集成：

```text
src/devices/             # 萤石摄像头及生理设备适配器
src/data/                # 视频、关键点、生理数据统一格式
src/models/              # YOLO、LSTM、多模态融合模型
src/inference/           # 统一推理编排和风险状态
src/api/                 # 风险、行为、生理数据接口
frontend/src/            # 风险看板和健康趋势
tests/                   # 各模块单测 + 真实设备联调测试
```

推荐先定义统一数据结构，再分别开发：

- `VideoObservation`：设备 ID、时间戳、检测框、关键点和帧质量；
- `VitalObservation`：设备 ID、人员 ID、时间戳、指标名称、数值和单位；
- `BehaviorEvent`：人员 ID、行为类型、开始/结束时间、置信度和是否紧急；
- `AlertEvent`：风险级别、触发原因、位置、通知状态和取消状态。

### 6. 最低可交付闭环

在 9 月 5 日前，至少要跑通以下闭环，才适合对外汇报：

```text
萤石摄像头 → YOLO 姿态 → LSTM/规则判定
                         ├─ 紧急：生成告警并通知
                         └─ 非紧急：记录行为并展示趋势
萤石生理设备 → 生理数据适配器 → 数据库 → 多模态展示/分析
```

最低验收项：

- 能从真实萤石设备获得视频和设备信息；
- 至少一种萤石生理设备完成一次真实数据回传；
- 跌倒、正常行走、蹲下或躺卧至少有可复现测试样本；
- 紧急告警和非紧急行为记录走不同处理分支；
- 子女端能看到风险状态和至少一种健康趋势；
- 所有演示数据注明是真实采集、训练数据还是模拟数据；
- 形成一份“代码版本—模型权重—数据版本—测试结果”对应表。
